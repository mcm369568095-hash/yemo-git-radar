# 数据源与已知坑

抓取层是整个技能最容易坏的地方——GitHub 说改就改。这份文档记录每个数据源怎么用、坏过什么、下次怎么修。

## 数据源 A：github.com/trending（官方涨星口径）

```
https://github.com/trending?since=daily|weekly|monthly
```

**为什么用它**：这是 GitHub 自己的"今天涨了多少星"统计，页面直接给数字，不用自己算。
其他所有"涨星榜"本质上都是在猜，只有这个是真数。

**怎么解析**：按 `<article class="Box-row">` 切块，每块里：
- 仓库名：只在 `<h2>...</h2>` 里面找 `href="/owner/repo"`
- 描述：`<p class="col-9...">`
- 语言：`itemprop="programmingLanguage"`
- 星/fork：`/stargazers"` 和 `/forks"` 链接的内文
- 涨星：`([\d,]+)\s+stars\s+(today|this week|this month)`

### 坑 1：href 不在 `<a>` 的第一个属性（2026-11 遇到）

页面结构改成了：
```html
<a data-hydro-click="{...一大坨...}" href="/owner/repo" ...>
```

原来的 `<a href="/([^"]+)"` 直接匹配不到，返回 0 条。

**修法**：先取 `<h2>(.*?)</h2>`，再在 h2 内部找 href。并且要排除 `sponsors` / `login` / `orgs` / `topics` 这几个链接——它们在每个 article 里都出现。

**怎么判断又改版了**：返回 0 条但 HTTP 200。这时候先 `print(html.count('Box-row'))`，
如果 Box-row 数量正常而解析结果是 0，就是正则挂了。

### 坑 2：UA 不是问题

试过 `Mozilla/5.0` 和自定义 UA，都能拿到完整页面。不用伪装浏览器。

## 数据源 B：GitHub Search API（新项目爆发榜）

```
GET /search/repositories?q=created:>YYYY-MM-DD stars:>=200&sort=stars&order=desc
```

**逻辑**：近 30 天新建 + 已有 200 星以上。这类项目的星几乎全部集中在最近，所以
"总星数"约等于"这 30 天的增量"，是新机会最好的代理指标。

**限量**：认证后 30 次/分钟，core API 5000 次/小时。
每次跑大概 1 次 search + 34×2 次 repo 详情/README ≈ 70 次，不会撞墙。

## 数据源 C：本地快照（越跑越准）

`data/history/YYYY-MM-DD.json` 存 `{repo: stars}`，下次跑算差额。

**这是唯一能算出"我们自己的真实增量"的办法**，前两个源都是别人给的口径。

### 坑 3：同一天跑两次，增量会变成个位数

第一次实现时，只要历史里有这个 repo 就用 delta 覆盖 trending 的涨星数。
结果同一天重跑，delta = 几小时内的增长 = +9，把 trending 的 +941 冲掉了。

**修法**：只有快照日期 ≠ 今天才用 delta，并且 delta 必须大于 trending 给的值才覆盖。

**首次运行没有历史**，这时涨星只能靠 trending 口径或 `stars/age` 推算。
推算值在报告里显示成"约 +N 星/天"，不要和官方口径混着看。

## 数据源 D：OSSInsight API（已放弃）

`https://api.ossinsight.io/v1/...` 能拿 star 历史曲线，看着很美。

**实测不行**：`/repos/{id}/stars/history` 返回 500，`/trends/repos` 超时。
不稳定到不能当核心依赖。留着当未来可选项，别写进主链路。

## 其他坑

### 坑 4：`public-apis` 这类超大清单混进候选

49 万星的清单类仓库，desc 是 "A collective list of free APIs"，
不以 `awesome` 开头，所以早期规则漏掉了。

**修法**：desc 里出现 `a list of` / `list of` / `collection of` / `collective list` / `curated list` 一律按清单处理。

### 坑 5：README 是中文却被判成"没中文"

早期用 `re.search("中文|chinese", blob)` 判断，逻辑反了——
搜的是"有没有提到中文"这个词，不是"内容是不是中文"。

**修法**：直接算汉字比例 `cjk_ratio(readme[:2000]) > 0.05`。

### 坑 6：形态判断把 web 应用当引擎库

`CopilotKit/OpenBot` 的 desc 里没有 dashboard/platform，只有 "AI coworkers that each get a computer"，
被判成引擎库，于是"改哪一处"给了个"补中文文档"，完全不对。

**修法**：关键词认不出时，再看 README 里有没有 `npm run dev` / `pnpm` / `next.js` / `react` /
`localhost:3000` 这类前端栈特征。有就是 web 应用。

### 坑 7：emoji 污染标题

很多项目的 desc 开头带 🐍🔥🚀，直接渲染出来一行里混着表情，显得很乱。

**修法**：`plain_what()` 里用正则清掉 U+1F300–U+1FAFF、U+2600–U+27BF 区段和变体选择符。

## 维护清单

GitHub 改版时按这个顺序查：
1. `fetch_trending('daily')` 返回几条？0 条 → 打印一个 article 看结构
2. `search_new(days=30)` 返回几条？0 条 → 看是不是 token 失效/限流
3. `repo_detail('某仓库')` 能不能拿到 license？None → 仓库可能改名了
4. 报告里数字对不对？对不上先查"坑 3"
