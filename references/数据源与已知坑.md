# 数据源与已知坑

抓取层是整个技能最容易坏的地方——GitHub 说改就改。这份文档记录每个数据源怎么用、坏过什么、下次怎么修。

## 数据源 A：github.com/trending（官方涨星口径）

```
https://github.com/trending?since=daily|weekly|monthly
```

**为什么用它**：这是 GitHub 自己的"今天涨了多少星"统计，页面直接给数字，不用自己算。
其他所有"涨星榜"本质上都是在猜，只有这个是真数。

**怎么解析**：按 `<article class="Box-row">` 切块，每块里：
- 仓库名：只在 `<h2>...</h2>` 里面找 `href="/owner/repo"`
- 描述：`<p class="col-9...">`
- 语言：`itemprop="programmingLanguage"`
- 星/fork：`/stargazers"` 和 `/forks"` 链接的内文
- 涨星：`([\d,]+)\s+stars\s+(today|this week|this month)`

### 坑 1：href 不在 `<a>` 的第一个属性（2026-11 遇到）

页面结构改成了：
```html
<a data-hydro-click="{...一大坨...}" href="/owner/repo" ...>
```

原来的 `<a href="/([^"]+)"` 直接匹配不到，返回 0 条。

**修法**：先取 `<h2>(.*?)</h2>`，再在 h2 内部找 href。并且要排除 `sponsors` / `login` / `orgs` / `topics` 这几个链接——它们在每个 article 里都出现。

**怎么判断又改版了**：返回 0 条但 HTTP 200。这时候先 `print(html.count('Box-row'))`，
如果 Box-row 数量正常而解析结果是 0，就是正则挂了。

### 坑 2：UA 不是问题

试过 `Mozilla/5.0` 和自定义 UA，都能拿到完整页面。不用伪装浏览器。

## 数据源 B：GitHub Search API（新项目爆发榜）

```
GET /search/repositories?q=created:>YYYY-MM-DD stars:>=200&sort=stars&order=desc
```

**逻辑**：近 30 天新建 + 已有 200 星以上。这类项目的星几乎全部集中在最近，所以
"总星数"约等于"这 30 天的增量"，是新机会最好的代理指标。

**限量**：认证后 30 次/分钟，core API 5000 次/小时。
每次跑大概 1 次 search + 34×2 次 repo 详情/README ≈ 70 次，不会撞墙。

## 数据源 C：本地快照（越跑越准）

`data/history/YYYY-MM-DD.json` 存 `{repo: stars}`，下次跑算差额。

**这是唯一能算出"我们自己的真实增量"的办法**，前两个源都是别人给的口径。

### 坑 3：同一天跑两次，增量会变成个位数

第一次实现时，只要历史里有这个 repo 就用 delta 覆盖 trending 的涨星数。
结果同一天重跑，delta = 几小时内的增长 = +9，把 trending 的 +941 冲掉了。

**修法**：只有快照日期 ≠ 今天才用 delta，并且 delta 必须大于 trending 给的值才覆盖。

**首次运行没有历史**，这时涨星只能靠 trending 口径或 `stars/age` 推算。
推算值在报告里显示成"约 +N 星/天"，不要和官方口径混着看。

## 数据源 D：OSSInsight API（已放弃）

`https://api.ossinsight.io/v1/...` 能拿 star 历史曲线，看着很美。

**实测不行**：`/repos/{id}/stars/history` 返回 500，`/trends/repos` 超时。
不稳定到不能当核心依赖。留着当未来可选项，别写进主链路。

## 其他坑

### 坑 4：`public-apis` 这类超大清单混进候选

49 万星的清单类仓库，desc 是 "A collective list of free APIs"，
不以 `awesome` 开头，所以早期规则漏掉了。

**修法**：desc 里出现 `a list of` / `list of` / `collection of` / `collective list` / `curated list` 一律按清单处理。

### 坑 5：README 是中文却被判成"没中文"

早期用 `re.search("中文|chinese", blob)` 判断，逻辑反了——
搜的是"有没有提到中文"这个词，不是"内容是不是中文"。

**修法**：直接算汉字比例 `cjk_ratio(readme[:2000]) > 0.05`。

### 坑 6：形态判断把 web 应用当引擎库

`CopilotKit/OpenBot` 的 desc 里没有 dashboard/platform，只有 "AI coworkers that each get a computer"，
被判成引擎库，于是"改哪一处"给了个"补中文文档"，完全不对。

**修法**：关键词认不出时，再看 README 里有没有 `npm run dev` / `pnpm` / `next.js` / `react` /
`localhost:3000` 这类前端栈特征。有就是 web 应用。

### 坑 7：emoji 污染标题

很多项目的 desc 开头带 🐍🔥🚀，直接渲染出来一行里混着表情，显得很乱。

**修法**：`plain_what()` 里用正则清掉 U+1F300–U+1FAFF、U+2600–U+27BF 区段和变体选择符。

## 维护清单

GitHub 改版时按这个顺序查：
1. `fetch_trending('daily')` 返回几条？0 条 → 打印一个 article 看结构
2. `search_new(days=30)` 返回几条？0 条 → 看是不是 token 失效/限流
3. `repo_detail('某仓库')` 能不能拿到 license？None → 仓库可能改名了
4. 报告里数字对不对？对不上先查"坑 3"

## 三档数据通路（2026-11-02 加）

不是所有用户机器都装 git、都有 token。所以数据通路做了三档，**任何一档都能出完整报告**。

| 档位 | 入口 | 消耗额度 | 拿不到什么 |
|---|---|---|---|
| FULL | `api.github.com/repos/{full}` + `.../readme` | 约 35 次/轮 | 无 |
| LITE | `github.com/{full}` 页面 + `raw.githubusercontent.com` | **0 次** | issue 数、仓库体积、创建时间 |
| OFFLINE | —— | —— | 全部 |

### LITE 为什么能零额度

两个反直觉的事实：

1. **`github.com/{owner}/{repo}` 页面里同时有 license 和完整 README。**
   一次请求（约 430KB）就能拿到，不用 API。license 以 `>Apache-2.0 license<` 这种锚文本出现，
   正则 `>\s*([A-Za-z0-9.\-+]{2,30})\s+license\s*<` 直接抓。
   README 在 `<article class="markdown-body">` 里，去标签即可（实测 kornia 拿到 61895 字符 HTML）。

2. **`raw.githubusercontent.com/{full}/HEAD/{file}` 是纯静态，不消耗任何额度。**
   `HEAD` 是 GitHub 支持的默认分支别名，所以不用先查默认分支叫什么。
   README/LICENSE 文件名不确定时按 `README.md → readme.md → README.rst → README.txt → README`
   顺序试，LICENSE 同理（含 COPYING）。

### 坑 8：缺字段不等于项目差，但也不能白送分

第一版 LITE 上线后，8 个候选全变 S 级，比 FULL 模式还高。原因很蠢：

`open_issues` 缺失时给 0，`0/stars=0` 落进最低档——这是对的。但 `created_at` 缺失时
`days_since(None)` 返回 9999，时效维度给 1 分；为了让替代逻辑生效，改成"用 gained 当替身"，
结果给了满分 10。两边一抵消，缺数据反而成了加分项。

**修法三条，缺一不可**：
1. `pushed_at` 缺失时不触发"一年多没提交"的淘汰 —— `days_since(None)=9999 > 365` 会误杀整个 trending 批次。
2. 替代分必须封顶：demand 用 gained 替代时上限 15（真实 issue 能到 20），fresh 上限 7（真实能到 10）。
3. 有 `_partial` 标记的，**总分再乘 0.94**。三项是估的就该整体打折，不能逐项按最好情况给。

改完 8 个 S 变成 8 个 A（77/77/71/70/70/69/69/69），和 FULL 模式的 72-78 分区间对上了。

### 坑 9：`_get` 遇限流傻等，最后抛错把整轮弄崩

原来 403 rate limit 会 `sleep(8*(i+1))` 重试三次，然后抛 `RuntimeError`。
匿名用户扫到第 20 个项目额度耗尽 → 整轮白跑 → 用户看到一堆 traceback。

**修法**：定义 `RateLimited` 异常，`_get` 命中限流就抛它。`process()` 捕获后：
- 把全局 `RT["mode"]` 切成 LITE，`RT["degraded"]=True`
- 当前这个项目立刻用网页通路重试
- 后面的项目全部走 LITE，不再碰 API

实测：API 调用次数停在 1 次，后续全部走页面，报告顶部标「中途降级」。

## 渲染自检的坑（改完版式一定要知道）

### 坑 10：headless Chrome 的视口最小 500px，看起来像"横向溢出"其实是截图裁的

`chrome --headless=new --window-size=390,900 --screenshot` 出来的图，右边总有一截被切掉，
文字像是溢出了屏幕。但这不是 CSS 的问题 —— `window.innerWidth` 实际是 **504**，
Chrome 新 headless 有最小窗口宽度，`--window-size` 小于它就被忽略，截图却按 390 裁。

**判定方法**（别靠眼睛猜）：

```html
<script>window.addEventListener('load',function(){
  document.title = 'inner=' + innerWidth + ' scroll=' + document.documentElement.scrollWidth;
  var over=[];document.querySelectorAll('*').forEach(function(el){
    if(el.getBoundingClientRect().right > innerWidth+1) over.push(el.tagName+'.'+el.className);
  });
  document.title += ' OVER:' + over.slice(0,5).join('|');
});</script>
```

塞进 HTML 末尾，`--dump-dom` 读 `<title>`：`scroll <= inner` 且 `OVER` 为空 = 没有溢出。
手机版式只能靠这条验，靠截图会一直误判成"要改 CSS"。

## 查重与建档的坑（2026-11-02 建）

### 坑 11：冷却期放宽时"重头全收"，会把当天的新项目全丢掉

`cooldown_pick` 第一版是**每档重新遍历**：7 天不够就看 14 天，还不够看 30 天……
到最后一档「不限」时重头收一遍，取前 N 个。

实测：8 个老项目 + 3 个新项目，要选 8 个。
- 7 天档：3 个新的能进，老的全被挡 → 不够
- 一路放宽到「不限」：重头遍历，按分数排老项目在前 → 前 8 个**全是老的**
- 结果：3 个新项目被判出局，当天所有新料作废

**正确做法是累加**：每一档只补「还缺的名额」，已经选中的不再动。
先收新技术，再用放宽的档补位。改完实测 3 新 + 5 旧，且 meta 里 `reused=5` 能标出来。

### 坑 12：同一天重跑，会被自己的账本挡住

查重一开始是「`last` 距离今天 ≥ N 天」。问题：早上跑了一次（记账日期=今天），
下午改个参数再跑，`gap=0`，8 个候选全被判定「刚推过」，换了一批全新的 ——
用户会以为雷达在乱跳。

**今天推过的一律不算历史重复**（`gap <= 0` 直接放行）。查重是为了「别天天推同一个」，
不是为了「同一天不许收敛到同一批」。

### 坑 13：记账必须在渲染成功之后

`_commit` 原来先记账再渲染。渲染一崩（比如模板变量名改了没同步），
那 17 个项目已经被记成「今天推过」，第二天全被冷却挡掉 ——
**用户什么都没看到，却被告知"这些昨天推过了"**。

顺序改成：写 `last_picks.json` → 渲染 → 渲染成功才 `_record`。
`fetch` 子命令则完全不记账：抓了没出报告，不该占冷却期。

### 坑 14：归档要存全量，但要去掉 readme

只存入选的 8 个，第二天查重够用，但攒不成知识库 ——
今天没进前 8 的项目，二十天后可能正是那个方向最值得做的。

但全量存 readme 会让一天一份档案涨到几百 KB。做法：`_slim()` 去掉 `readme` / `detail`，
`analy` 只留 `zh / plain / gap / buyer / _auto` 五个字段。实测一天 33 KB，一年 12 MB，可以接受。

### 坑 15：方向池的详情名额会被老项目吃光

方向池 62 个项目，绝大多数是几万星的存量老项目，粗排 `gained*3 + stars^0.6` 永远排前面；
今天刚上榜的新项目星少、涨星 0，按 rough 排序根本进不了前 24 个详情名额。

实测第一版：`今日新上榜 0 个、涨星中 0 个、既往高星 9 个` —— 三块只剩一块，
而「今日新上榜」恰恰是用户最想要的。

修法：`collect_focus` 给全站榜命中的项目打 `_priority`，`process` 里保底前 12 个名额。
改完 `今日新上榜 1 个`（那天这个方向确实只有 1 个在榜，不是 bug）。
