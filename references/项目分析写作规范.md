# 项目分析写作规范

> 这份文件是给「Agent 精修」这一步用的。规则版脚本只能把英文词换成中文词，
> 真正让人看懂的东西（这东西等于什么、谁会买、为什么买）必须人来写，或者模型来写。
> 写之前先读一遍，写完对着最后一节的「自检」过一遍。

---

## 一、为什么要四层，不是一句

GitHub 的简介是写给工程师看的。

> Create and share beautiful images of your source code

工程师扫一眼就懂：代码截图美化工具。但一个想在 GitHub 上找副业的人看完还是不知道：
**这东西长什么样？我能拿来干嘛？跟我有关系吗？**

所以一句原文不够，要拆成四层，每一层回答一个问题：

| 层 | 回答什么 | 写错的后果 |
|---|---|---|
| 原文 | 作者到底怎么说的 | 删了就没法核对，出问题说不清 |
| 直译 | 这句英文准确的中文是什么 | 译歪了，后面全歪 |
| 说人话 | 这等于什么？跟我有关系吗 | 用户看不懂就翻页走了，整份报告白做 |
| 能干什么·怎么用 | 具体拿它做什么、怎么跑起来 | 看着有用，但不知道怎么下手 |

**顺序不能反**。先给原文（可信），再给译文（准确），再给比喻（好懂），最后给场景（能用）。

---

## 二、直译怎么写

四条：

1. **一字一句译准，不演绎**。`Create and share` 是"生成并分享"，不是"一键生成分享"。
2. **保留专有名词原样**。`PowerPoint`、`Markdown`、`Docker`、`SEO` 不译。
3. **技术词译成通用说法**。`harness` → "一站式工具"，`inference` → "跑模型"，`schema` → "结构化数据"。
4. **原文有毛病就照译，再在说人话里补**。原文写"100+ LLMs"，直译就是"100 多个大模型"，
   不用替它修饰成"支持主流大模型"——那是编。

反例：

- ❌ `AI turns documents or topics into real, native PowerPoint decks`
  → "AI 把文档变成 PPT"（丢了 native，而 native 恰恰是这项目最值钱的点）
- ✅ "AI 把文档或题目变成真正的 PowerPoint——原生形状、转场动画、按需生成图表，还能按讲稿配音"

---

## 三、说人话怎么写

**公式：说白了，这是一个【类比】，它干的事是：【一句话】**。

类比的来源（按形态取）：

| 形态 | 类比怎么写 |
|---|---|
| web 应用 | "打开网页就能用的小工具，不用装东西" |
| 引擎库 | "一堆写好的能力，但没有界面，得有人包一层壳" |
| 命令行 | "要在黑框里敲命令才动起来的工具，功能硬但上手要人带" |
| Agent 技能 | "一份写给 AI 的操作手册，装进去它就知道按你的规矩干活" |
| 模板主题 | "一套现成模板，把内容换掉就能发布" |
| 模型数据 | "一个能跑 AI 的模型，得自己配环境才能动" |

再加**一个生活化的比方**，让人一秒有画面：

- carbon → "给代码拍证件照"
- hyperframes → "用做网页的方式做视频"
- taste-skill → "给 AI 加一份审美说明书"
- claude-seo → "像 SEO 顾问一样把网站从头查到尾"

比方要**具体、可想象、不夸大**。写"这是革命性的 AI 平台"是废话，写"给代码拍证件照"才是人话。

---

## 四、能干什么 · 怎么用

**能干什么写三条，第一条必须是他明天就能用上的**，不是"可用于多种场景"。

排序原则：
1. 最日常的用法（写文章、做课件、出图）
2. 能变成收入的用法（接单、代做、给客户交东西）
3. 能放大成产品的用法（做成工具站、矩阵号、付费产品）

**怎么用写 3-4 步，写到"第一步点哪里"的程度**：

- ❌ "安装并配置环境后使用"
- ✅ "装 Node，跑 npm init slidev；在 slides.md 里按格式写内容；浏览器预览；导出 PDF"

如果第一步最容易卡（比如要 Docker、要 Node、要显卡），**就在这一步后面加括号说明**
（"这一步最容易卡住"），这是给用户的预期管理。

## 五、差哪一步

这一段原来是「改哪一处」，改名了，因为它回答的是**同一个问题的后半句**：
"这项目能用，但凭什么我要买你的版本？"——凭你把这一步补了。

写法：**先指出缺什么（具体），再说补什么（今晚能干完），最后说补完值多少**。

- ❌ "优化中文体验"
- ✅ "主题全是国外审美、默认字体不带中文，粘中文代码进去排版就散。做一套中文排版预设 + 20 个中文主题，才有人愿意为「省事」付钱。"

判断标准：**这句话能不能直接当今晚的待办清单**。不能，就是还没写到位。

---

## 六、卖给谁 · 为什么买

「卖给谁」写**适用者**，要具体到"能搜到这个人"的程度：

- ❌ "开发者"、"AI 用户"
- ✅ "接单的前端/设计"、"做课件的老师"、"写技术公众号的号主"

「为什么买」是**卖点**，不是买家描述的重复。公式：

> 【买家】不是不会做，是【懒得/不敢/没时间】为【这一步】花【多大代价】。
> 你把「【差哪一步】」替他们做完，他们花的钱远少于自己折腾的时间。

三条自检：
1. 这句话能不能说服你自己掏钱？
2. 有没有说清"省的是时间还是钱"？
3. 有没有踩到他的**具体痛处**（"被 AI 味坑过，客户一眼看出来就砍价"比"提升效率"痛一百倍）。

---

## 七、自用 / 打包出售：两个方向，别混

这两栏回答的是**两个不同的人**的问题，所以必须分开写。

### 自用（用户自己就是用得上的人）

回答：**我拿它省什么？** 三种可选的答案，写到具体动作上：

- **省时间**："一次出图省十分钟，原来调七八个主题"
- **省内容成本**："一套模板存下来，以后所有视频风格统一"
- **攒方法论**："你会摸清哪一步该交给 AI、哪一步必须人改，这个分工经验能复用到所有活上"

第三种最值钱，因为它跟着人走，不会因为工具过时而失效。

### 打包出售（用户想把它做成商品）

回答：**具体怎么把它变成一件能卖的东西？** 要包含四件套：

1. **改造成什么**（汉化 + 模板 + 一键脚本）
2. **装成什么形态**（zip 发网盘 / 在线服务 / 安装包 / 教程）
3. **怎么定价**（9.9 起测 / 99 起 / 按次 / 订阅）
4. **主图和标题怎么写**（"改前 vs 改后"对比图、"代码截图太丑？"）

- ❌ "可以包装成商品出售"
- ✅ "汉化版 + 20 套中文主题 + 一键导出小脚本，打包发网盘。主图用「改前 vs 改后」两张代码图对比，标题写「代码截图太丑？」，定价 9.9 起测，卖得动再加套餐。"

---

## 八、深挖（单独重点）多写一段

`radar.py deep` 出来的那个 tab，除了上面全部内容，还要写 **门槛与风险**：

- 技术门槛（要服务器？要显卡？要会 Docker？）
- 竞争门槛（"已经有人做过中文版"必须说，不说就是不老实）
- 真正的门槛在哪（"不在技术，在审美"这种判断才值钱）
- 平台风险（大厂随时自己做掉、许可证有坑）

---

## 九、交付前自检（逐条打勾）

- [ ] 原文照抄，一个词没删
- [ ] 直译准确，专有名词保留
- [ ] 说人话里有一个生活化的比方，不是"强大的 AI 工具"这种空话
- [ ] 能干什么三条，第一条明天就能用
- [ ] 怎么用写到"第一步点哪里"，最易卡的一步有提醒
- [ ] 差哪一步能直接当今晚的待办
- [ ] 卖给谁具体到能搜到人
- [ ] 为什么买说清了"省时间还是省钱"，且踩到具体痛处
- [ ] 自用写了省什么（时间/内容/方法论至少一项）
- [ ] 打包出售有形态 + 定价 + 主图思路
- [ ] 没有出现"赋能""闭环""生态""一站式解决方案"这类词
- [ ] 没有编造作者没写过的事实（做不到就写"作者没写，需要打开仓库确认"）
